# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this project is

`priority-ledger.html` is a single self-contained file (HTML + CSS + JS, no npm dependencies) hosted on **GitHub Pages** as the app's only home (cross-device, login-gated, synced via Supabase). It's a personal task tracker for the project owner: four categories (Family Business, Game & Software, Estate Upkeep, Personal/Misc), plus a Daily tab for day-by-day priority lists.

`priority-ledger.html` itself is **generated output**, not source — never hand-edit it. It stays a single file at the point GitHub Pages serves it (deploy is still "just push the file," no build step for the *user*), but the editable source underneath it is split into small feature-scoped files under `src/`, joined back into `priority-ledger.html` by `build.py`. See "Source layout & build" below before editing anything.

## Source layout & build

Source of truth is `src/`:

- `src/shell-head.html` — `<!DOCTYPE>`/`<head>` through the opening `<style>` tag.
- `src/styles.css` — the entire stylesheet (no `<style>` tags — `build.py` adds those).
- `src/shell-body.html` — `</style>` through `</head>`/`<body>`/all static markup, through the opening `<script>` tag.
- `src/js/NN-name.js` — the script body, split into 19 feature-scoped modules (numbered so both the filesystem and `build.py`'s explicit list show the assembly order at a glance):

  | file | covers |
  |---|---|
  | `01-categories-theme.js` | category/location defaults, `CATEGORIES` index, theme color math (`shadeHex`, `relLuminance`, `applyThemeObject`) |
  | `02-storage-state.js` | Supabase config, session load/save, `storage` adapter, `defaultState`/`normalizeState` |
  | `03-sync-save.js` | cross-device refresh polling, `saveState`/`queueSave` retry logic |
  | `04-undo.js` | `pushUndo`/`undo`/`redo`, undo status UI |
  | `05-dates-sort.js` | date parsing/formatting, `sortTasks`, sort-mode handling |
  | `06-tabs-render.js` | `visibleTabs`, tab bar rendering, taglines, location badge |
  | `07-drag.js` | task/subtask drag-reorder handlers |
  | `08-render-core.js` | `taskRowHtml`, `render()`, `renderList()`, `switchTab`, page-tilt/tag helpers |
  | `09-settings.js` | Settings panel: category/location management |
  | `10-claudeview.js` | the plain-text Claude-readable view |
  | `11-daily-core.js` | Daily tab: month/day list, day summaries |
  | `12-daily-tree.js` | Daily tab: the "add to this day" tree picker |
  | `13-checklist.js` | checklist category type: overview, detail, pending views |
  | `14-task-actions.js` | day-planning actions (plan/unplan/move-to-tomorrow), timeframe/priority updates |
  | `15-subtask-edit.js` | inline subtask title/date editing |
  | `16-task-crud.js` | core task/subtask CRUD (add/toggle/delete/update) |
  | `17-auth-ui.js` | location toggle, auth form submit, sign-out, `enterApp()` |
  | `18-calendar.js` | calendar category type: month grid, month nav, `openCalendarDay()` |
  | `19-bootstrap.js` | the Esc/undo keydown listener, resize/beforeunload listeners, the `init()` IIFE — **must stay last**, see note in `build.py` |

- `src/shell-foot.html` — `</script>`/`</body>`/`</html>`.

**Function order inside the concatenated script doesn't matter** — it's one shared scope and function declarations hoist — so a function can live in whichever module matches its feature even if that's not where it physically sat before the split. The one real constraint is `19-bootstrap.js` staying last, since it contains the `init()` IIFE and event-listener registrations that read globals defined throughout the other modules.

**Workflow**: edit files under `src/`, then run `python3 build.py` to regenerate `priority-ledger.html` before testing or committing. Claude Code should run this itself automatically as part of finishing any task or preparing a commit — no need to ask first, just run it. Never edit `priority-ledger.html` directly; the next build silently overwrites hand edits there.

The architecture notes below still describe behavior accurately regardless of which module a function now lives in — use `grep -rn 'functionName' src/` to find it rather than assuming a specific file.

## Architecture (read before editing)

- **State** lives in one in-memory object: `state = { location, tasks: [], days: [], categories: [], locations: [], locationEnabled, theme }`. Everything persists as one JSON blob under a single storage key (`tracker-state`) — don't split it into multiple keys.
- **Storage**: all reads/writes go through the `storage` adapter defined near the top of the `<script>` block, not `window.storage` directly. Always call `storage.get`/`storage.set` — never bypass the adapter. It tries three sources in priority order:
  1. `window.storage` — the real Claude.ai artifact storage, present only when pasted into a claude.ai conversation.
  2. Supabase (Postgres + Auth + REST, via plain `fetch` — no supabase-js dependency) — the primary path for the hosted app. Each signed-in user has exactly one row in the `ledger_state` table, keyed by `user_id`, protected by a Row Level Security policy (`auth.uid() = user_id`) so the same public anon key can't be used to read/write another user's data. Auth tokens are refreshed via `ensureFreshSession()` before every call; if refresh fails, `forceReauth()` clears the session and kicks back to the login screen rather than silently degrading storage.
  3. `localStorage` — **only** when the user explicitly picks "Continue without an account" on the login screen (`localOnlyMode = true`). This is single-device local testing, not a network-failure fallback — storage never silently drops from Supabase to `localStorage` on its own, since that would mean data quietly stops syncing without the user knowing.
- **Saving**: `queueSave()` sets `unsavedChanges = true` and chains a `saveState()` call onto `saveChain` (see Conventions below for the render-then-queueSave ordering). `saveState()` itself retries on failure with capped exponential backoff (`SAVE_RETRY_DELAYS_MS`, topping out at 30s) rather than giving up after one attempt — a transient network blip must never silently drop an edit that only exists in memory. `delayOrOnline()` cuts a retry wait short the moment the browser reports connectivity again, instead of always sitting out the full backoff. The one error that stops retries immediately is `'session expired'`: `storage.set()`/`storage.get()` already call `forceReauth()` and send the user back to login in that case, so retrying can't succeed, and the pending edit will be superseded by `loadState()` pulling fresh data on the next login anyway. `unsavedChanges` flips back to `false` only once a save actually succeeds, and gates a `beforeunload` handler that warns before closing/reloading the tab with a save still pending — the last line of defense against losing an edit that the retry loop hasn't gotten to yet.
- **Auth**: `SUPABASE_URL` / `SUPABASE_ANON_KEY` near the top of the script hold the project's public config (safe to be public — RLS is what actually protects data, not the key). Login/signup UI lives in `#authShell`; the app itself lives in `#appShell`; `init()` decides which to show on load.
- **Categories are per-user data, not config**: `state.categories` is an array of `{ id, label, hex, locations }` (`locations` here is which location ids the tab shows under), in display order — `moveCategory(id, ±1)` reorders by splicing the array, which is all `tabOrder()` needs since it builds the tab list straight from `['all', ...state.categories.map(c=>c.id), 'daily']`. `CATEGORIES` is a plain id-keyed lookup object rebuilt from `state.categories` by `rebuildCategoriesIndex()` on every load and every category mutation (including reorders, since `Object.entries(CATEGORIES)` — used by the category `<select>`s — depends on object key insertion order too) — call sites still read it as `CATEGORIES[key]` like before, they just can't assume it's static. `defaultCategories()` seeds new accounts (and migrates pre-existing accounts that predate this feature, via `normalizeState()`) with its current set — three `standard` categories plus one `checklist` category ("Lists"), included in the defaults so a new account sees a working checklist tab without first discovering "Settings → add a tab → Checklist" on their own. Deleting a category never touches tasks — a task keeps whatever `category` id it already had, and once no tab matches that id it just falls back to showing under "All" only, styled via `FALLBACK_CATEGORY` in `taskRowHtml`. That's the whole safety mechanism against losing tasks to a deletion; don't add a separate "reassign tasks" step, it's redundant.
- **Calendar is a third category type** (`type:'calendar'`, alongside `'standard'`/`'checklist'`) — see `isCalendarCategory()` in `01-categories-theme.js` and `renderCalendar()`/`openCalendarDay()` in `18-calendar.js`. Unlike a checklist category, it owns no tasks of its own (no `t.category === thisId` data exists anywhere) — it's a whole second view onto the exact same `state.days`/`plannedDates` data the Daily tab already lists day-by-day, just gridded by month via `dayItemsSummary()` per cell instead of listed one day at a time. Made a real, addable/deletable/colorable category type rather than a second fixed tab like Daily itself is, specifically so it's opt-in. Clicking any date (whether or not it's in `state.days` yet — `openCalendarDay()` calls `ensureDay()` first, same "only pushUndo if this actually creates a new day" rule `addDay()`/`confirmPickDate()` already follow) switches to the Daily tab and opens that day's own detail page — it doesn't duplicate that page under the calendar tab. The month grid's own compact `pageTagHtml(..., true)` "Today" trigger is styled by the exact same dev pendingTagStyle/pendingTagColor settings the checklist's "Pending" trigger uses, automatically, since both are just `.pagetag.compact` — no calendar-specific styling hook needed or wanted.
- **Locations are also per-user data**: `state.locations` is a fixed-size array of `{ id, label }` (ids stay `'MA'`/`'Argentina'` forever so category `.locations` arrays never need migrating — only `label` is user-editable), plus `state.locationEnabled` to turn the whole feature off. When disabled, `visibleTabs()` ignores per-category `locations` entirely and the location badge (`#locBadge`) is hidden — don't add a second code path for "no locations configured," disabled IS that path.
- **Settings** (gear icon, `#settingsBtn`, top-left of the masthead) is a single panel (`renderSettings()` → `#settingsView`) covering both tab management (add/rename/delete, delete gated behind an explicit "N tasks will move to All" confirm, plus up/down reorder via `moveCategory`) and location config (enable toggle + label editing) together — it replaced an earlier "⚙ Tabs" entry that lived in the tab row itself; keep both concerns in this one panel rather than re-splitting them out. Uses the "stacked page" pattern (see below) — wraps in `.stackedpage` with `pageTagHtml('toggleSettings()', 'Done')` as the close tag, no separate bottom "Done" button (same as the checklist detail/pending views this pattern was first built for — Esc also closes it, per the keydown listener below, so the tag isn't the only way out).
- **Undo/redo** (`undoStack`/`redoStack`, bottom of `#appShell`) is whole-`state` snapshotting, not hand-written inverses per action — `pushUndo(label)` deep-clones `state` via `JSON.parse(JSON.stringify(state))` and must be called as the *first* line of any new content-mutating function, before the mutation, with a human-readable label (e.g. `` `Deleted "${t.title}"` ``). This is deliberate: with ~25 different mutation functions, a whole-state clone can't drift out of sync the way a per-action-type inverse could if someone added a mutation and forgot its undo counterpart. Two things are NOT on the undo stack: pure navigation (`switchTab`, `toggleLocation`, opening/closing a day — these change what you're looking at, not your content) and no-op edits (blurring a text field without changing its value — guarded inline, e.g. `if(newVal && newVal !== c.label)`, so an empty click-in-click-out doesn't waste a stack slot). `undo()`/`redo()` call `afterStateRestore()` after swapping `state` in, to fix up transient UI state (`activeTab`, `selectedDay`) that might now point at something the restored snapshot doesn't have. Both stacks reset in `enterApp()` and `signOut()` — undo history is scoped to one login session, never persisted, never crosses accounts.
- **Esc key** (global `keydown` listener near the bottom of the script) closes whatever's most local first: an open task detail (`.expand.open`) beats the Settings panel beats jumping to the "All" tab — check `settingsOpen` and `.expand.open` before falling back to `switchTab('all')`. The same listener drives Cmd/Ctrl+Z (undo), Shift+Z or Ctrl+Y (redo), guarded to skip entirely when focus is in an `INPUT`/`TEXTAREA`/`SELECT` so native in-field undo isn't hijacked. `switchTab(key)` itself also resets `claudeView`/`settingsOpen` before setting `activeTab` — the tab bar stays visible and clickable through both overlays (they don't cover it), so without this a tap on a tab would just update `activeTab` behind the still-open overlay instead of visibly going anywhere. No `key === activeTab` early return either: clicking the tab you're already "on" while Settings or the Claude view is open must still exit it, same as pressing Esc would. `closeClaudeView()` (used by both its page tag and this Esc handler) sets `settingsOpen = true` rather than just clearing `claudeView` — the only way into that view is the "Open Claude-readable view" button inside Settings, so leaving it should return there rather than to whatever category tab happened to be active underneath.
- **Theming** (`state.theme = { bg, paper, gradient, grain, pages, leather }`, per-user, editable in Settings → Appearance) drives CSS custom properties at runtime via `applyThemeObject()` — it does NOT touch `--paper`, which stays permanently fixed to the classic cream and is used only for things that sit against the (also customizable) desk background outside the card, like the masthead title. The actual customizable "ledger surface" color lives in `--card-bg`/`--card-bg-dim`; if you add a new UI element that should visually read as part of the ledger card (not the desk behind it), use `--card-bg`, not `--paper` — mixing the two is exactly the bug this split exists to prevent. `--ink`/`--ink-soft`/`--line` are derived from `paper`'s luminance (`relLuminance()`), not user-set directly, so text stays legible no matter how dark or light a "ledger" color someone picks.
  - `shadeHex(hex, percent)` darkens/lightens **multiplicatively** (scales each channel, doesn't add a flat offset). This matters: an additive offset clips a dark color like the classic desk green to near-black almost immediately (its channels only start around 40-54), which is exactly the "intense gradient" bug from an earlier version. Multiplicative scaling preserves the color's own character at any base lightness — don't switch this back to additive.
  - `gradient`, `grain`, `pages`, and `leather` are four **independent** booleans, not an exclusive choice — they're meant to layer (e.g. grain + pages + leather together). `gradient` defaults to `false` (flat `--desk`/`--desk-dark`, matching the classic pre-theming look and the login screen, which never calls `applyTheme()` at all); when on, `--desk-dark` is `shadeHex(bg, -0.30)`, which reproduces the original hand-picked `--desk-dark` almost exactly for the default green — that specific constant isn't arbitrary, don't casually retune it.
  - `grain` (noise `::before`, inline SVG `feTurbulence`, no external asset) is paired with an **inset box-shadow vignette** on `#appCard.texture-grain` itself (darkens toward the edges) — the vignette is what makes it read as an aged page rather than a flat static overlay; noise alone wasn't noticeable enough.
  - `pages` is a single rotated `::after` (not box-shadow-on-the-card) with its own `box-shadow` layers and a squarer `border-radius` than the card's — a real rotated rectangle behind the card reads as an actual sheet of paper peeking out; the earlier version used parallel diagonal box-shadow lines on the card itself, which didn't have a sense of "shape" independent of the card's own rounded corners. Its `clip-path` gives the right/bottom edges (the ones that actually peek past the card — top/left stay straight since they're hidden regardless) a torn/deckled look, plus `filter: blur(0.4px)` to soften the cut. Keep notch depth in that clip-path under ~1.5%: the percentages are against the whole card-sized box, so anything bigger reads as a harsh regular sawtooth, not paper fiber — this was tried and visibly wrong once already. Its `transform` reads a `--page-transform` custom property (CSS vars cascade to pseudo-elements) that `randomizePageTilt()` sets to a random pick from `PAGE_TILTS` on every `switchTab()`, so the tilt/offset shift a little each time you change tabs, like the stack shifting underneath. The `rotate(-2deg)` in `transform: var(--page-transform, rotate(-2deg))` is only the pre-first-switch fallback.
  - Because `grain` uses `::before` and `pages` uses `::after`, they don't collide and can be combined freely — don't consolidate them onto a single pseudo-element, that's what would force them back into being mutually exclusive. `.card` has no `overflow:hidden` (removed on purpose) so `pages`'s `::after` can extend past the card's edges; `grain`'s `::before` clips itself via `border-radius:inherit` instead of relying on the parent's overflow.
  - `leather` is a real wrapper element, `#leatherCover` (`.leathercover` in HTML, wraps `#appCard`) — NOT a pseudo-element, because `#appCard`'s own `::before`/`::after` were already spoken for by grain/pages. Off by default it contributes no padding/background/box-shadow at all (zero layout impact); on, it adds its own `::before` (a coarser/marbled `feTurbulence type='turbulence'` noise, deliberately different from the paper grain's fine `fractalNoise` — leather and paper are different materials, they shouldn't share a texture recipe) and `::after` (a dashed inset border suggesting hand-stitching). Also has no `overflow:hidden`, same reasoning as `.card` — so a poking `pages` sheet underneath isn't clipped by the cover around it. If you add a fourth appearance toggle that needs its own pseudo-elements, it'll need its own wrapper element too, for the same reason. `.card`'s `z-index:1` (not just the `0` needed to contain its own `::after`'s stacking) is what keeps the card painting above `.leathercover`'s `::before`/`::after` — without it the stitching border, generated last, painted last (i.e. on top of the card and its poking page). If you add more layers to either element, re-check this ordering rather than assuming DOM order alone will do the right thing.
  - `resetTheme()` restores `defaultTheme()` exactly (bg/paper colors, gradient/grain/pages/leather all off) — that IS the "go back to these colors" the project owner asked to keep available.
  - `applyTheme()` (reads `state.theme`) runs after `loadState()` in `enterApp()` and inside `afterStateRestore()` (so undo/redo of a theme change repaints immediately); `signOut()` calls `applyThemeObject(defaultTheme())` directly (not `applyTheme()`) since there's no logged-in `state` to read at that point — the login screen always shows the classic look regardless of what the previous user had set.
  - `normalizeState()` migrates the short-lived single-choice `theme.texture: 'flat'|'grain'|'pages'` shape (texture used to be exclusive, before it became independent booleans) into `grain`/`pages` booleans, and backfills `gradient`/`leather` for anyone whose saved theme predates them — keep these migrations in place, accounts saved during those windows still have the old shapes.
- **Tab bar** (`.tabs`) carries its own shared translucent backing panel (rounded top corners, `margin-bottom:-1px` to sit flush against the card) rather than the seamless-attachment trick living on each `.tab` individually — with enough categories to wrap to multiple rows, only the last row touched the card under the old per-tab approach, so earlier rows just read as loose pills floating in open space. Keep the "attached to card" affordance on the container, not per-tab, so it still looks like one header block regardless of row count.
- **Rendering**: no framework, just template strings + `innerHTML`. `taskRowHtml(task, showDot, inDaily)` is the single shared renderer for a task row — used both by the normal category tabs and by the Daily day-detail view. Edit it once, both places update. Don't fork it.
- **"Stacked page" pattern** (`.stackedpage` + `pageTagHtml()` → `.pagetag`/`.pagetagtip`/`.pagetaglabel`, all defined once near the top of the `<script>` block next to `escapeHtml`) is the reusable way to make a view read as its own page layered on top of whatever's beneath it, with a flag/tag "back" (or, for `.pagetag.compact`, a small forward-navigation trigger) instead of a plain `.backbtn` text link. First built for the checklist list-detail/pending views, then Settings and the Claude-readable view (`renderClaudeView()`), now also Daily's own day-detail (`renderDayDetail()`) — every full-panel drilldown in the app uses it at this point. Reach for this pair again for any future one, rather than inventing a new one-off look or defaulting to a plain `.backbtn`. See the checklist and Settings bullets below for more on the current uses and the CSS comments on `.stackedpage`/`.pagetag` in `<style>` for the geometry.
- **`.substack` (a standard task's linear subtask-progress bar, `subProgressHtml()`)** uses `display:grid; grid-auto-flow:column; grid-auto-columns:1fr` for its N equal-width `.subpip` children, not `display:flex` + `flex:1` — flexbox's fractional-width rounding for `flex:1` items tends to dump the leftover remainder pixel onto whichever item comes last, which read as the first few pips being a visibly different size than the last few (worse at non-100% browser zoom, since that rescales the already-fractional division against a new pixel grid); Grid's `fr` unit distributes that remainder more evenly across tracks instead. `grid-auto-columns` (not a hardcoded `grid-template-columns`) is what lets this keep working without knowing the pip count ahead of time.
- **Checklist list rows** (`checklistListRowHtml()`) use a round `.checkcircle` instead of the square `.check`, with the list's items shown around it (`checklistProgressHtml()`) rather than the linear `.substack` used under a standard task's `.check` (`subProgressHtml()`) — a deliberate visual split between the two category types, not something to unify. `.checkcircle-wrap` is a fixed-size box (34px) regardless of item count, with pegs/ring positioned absolutely inside it, so rows stay column-aligned the same way `.checkwrap` does. At or under `CHECKLIST_PEG_LIMIT` (12) each item gets its own fixed-size `.peg` — a genuine rectangle, not a `conic-gradient` arc slice (those are wedges, wider at the outer edge, which read as trapezoids rather than boxes) — at a fixed slot angle (`PEG_START_DEG + i*PEG_SLOT_DEG`, `i` = the item's index). Each `.peg` sits inside its own `.pegpivot`: a zero-size point at the container's exact center (`top/left:50%` of an even-pixel box lands on a whole pixel) that carries the `rotate()`, rather than the rotation and the centering fraction both living on `.peg` itself (a fractional `margin` *and* a fractional `transform-origin` that have to cancel exactly) — two independent fractional values are more room for cross-browser rounding to drift apart than one. `.peg`'s own width (`6px`, an even number) keeps its one remaining centering fraction (half-width) a whole pixel too. At this spacing, adjacent pegs' corners slightly overlap, so the `filled` class (a done item) goes on `.pegpivot`, not `.peg` — `.pegpivot`'s own `transform` gives it its own stacking context, so `z-index` set on the inner `.peg` would only reorder within that one pivot, not against sibling pivots; `.pegpivot.filled{ z-index:2 }` vs the default `1` is what guarantees a filled peg always paints over an unfilled neighbor regardless of which one happens to come later in the item array. Each `.pegpivot`'s inline `transform` also always carries a trailing `translateZ(0)` alongside the `rotate()` — purely a rendering-consistency hack, not a visual change: `rotate(0deg)` (which a peg lands on exactly whenever a slot sits on a cardinal axis, since `PEG_START_DEG`/`PEG_SLOT_DEG` are chosen so that happens) can get treated by the browser as an identity transform and painted via the plain layout path instead of the GPU-composited one every other (genuinely rotated) peg uses, which rounds fractional device pixels differently at non-100% browser zoom — invisible at 100%, but that one peg reads as a slightly different size at other zoom levels otherwise. `translateZ(0)` forces the same layer promotion regardless of the rotation angle, so every peg round-trips through the identical rendering path. `.peg` also carries no `opacity` — its colors are flat opaque fills, not a translucent tint, so two overlapping unfilled pegs blend into the same flat color at the seam instead of stacking into something visibly darker the way a translucent overlap would. The softer look an unfilled peg used to get from that opacity is baked into its actual color instead, via `color-mix(in srgb, var(--card-bg-dim) 60%, var(--card-bg) 40%)` (and the border similarly) — same "60% peg color over the card" result as the old opacity, but as one flat color, so it doesn't reintroduce the overlap-darkening problem. Slot size and radius never change with item count: a 3-item list only fills its first 3 slots and leaves the rest of the ring bare, rather than 3 big pegs stretched to fill the whole circle the way one shared `conic-gradient` ring divided by item count used to (that was also what made those segments trapezoidal, and it meant every peg resized and shifted whenever an item was added anywhere in the list — fixed slots mean an item's peg is stable for the life of the list). Past the threshold it falls back to a single smooth `.progressring` percentage sweep, since that many discrete slots stops reading as separate pegs; its `conic-gradient`'s `from ${PEG_START_DEG}deg` keeps its 0% point aligned with peg slot 0, so the two modes share the same starting point when a list crosses the threshold. `PEG_START_DEG` is `-30`, not `0` or an arbitrary "top-left-ish" value — it has to stay a multiple of `PEG_SLOT_DEG` (30°), since 90° (the gap between the four cardinal directions) is exactly 3 slots, which is what guarantees the slots nearest top/right/bottom/left land exactly on those axes instead of sitting at a visible off-angle. `.progressring`'s `inset:5px` (not `0`) is what keeps its visible band thin (~3px against the 18px `.checkcircle`) — going back to `inset:0` was the "way too thick" original version. Either way the opaque `.checkcircle` sits centered on top (`z-index`, not DOM order) and masks the middle, so no separate donut-cutout element is needed. `checklistPendingItems(t)` — used by both the overview's pending count and the "all pending items" view — returns `[]` for a list whose own `status` is `'done'` regardless of its items' individual `done` flags: marking a whole list complete is meant to retire it from "pending" everywhere, even if some items were never individually checked off.
- **Checklist item checkboxes** (inside a list's own detail view, and in the "all pending items" view) use `.subcheck.circle` — `.subcheck` unchanged plus a `border-radius:50%` override — to match `.checkcircle`'s circular language. A standard task's own subtasks keep plain `.subcheck` (square), since those go with its square `.check`; don't apply `.circle` there.
- **The checklist list-detail view and its "all pending items" view** (`renderChecklistDetail()`, `renderChecklistPending()`) use the "stacked page" pattern above: both wrap their content in `.stackedpage` and call `pageTagHtml('close...()', label)` for the back tag. `renderChecklistDetail()` also runs a large header at the top of the page — `checklistCheckcircleHtml(t)` (the same `.checkcircle-wrap` markup `checklistListRowHtml()` uses for the small icon next to each overview row, factored out specifically so the two can't drift out of sync) inside `.checklistheader`, which scales it up via CSS `transform` rather than a second hand-tuned set of peg/ring sizes. `.checklistheader` is given an explicit `height` sized to fit the scaled-up result — `transform` doesn't affect layout box size, so without that the flow box would stay the original 34px and the visual overflow could collide with neighboring content. Its bottom margin is negative on purpose, pulling the title up close enough to read as this header's own caption rather than a separate block. The title input right under it gets a `.checklisttitle` modifier (bigger, centered — a page header, not the small inline-edit field a standard task's own title looks like) and `.taskmeta` gets a matching `.checklistmeta` modifier (centered, faded) for the created-date line beneath it; both are modifiers on the shared `.titleedit`/`.taskmeta` classes specifically so the standard task expand view (which reuses both) is untouched. Each item row gets a `listdone` class when its *list's* `status` is `'done'` (not from the item's own `done` flag) — dims the whole row via `opacity` rather than only restyling `.subtext`, so a not-yet-individually-checked item still reads as complete once its list is marked done, without ever touching that item's actual `done` flag (so un-completing the list instantly restores each item's real individual state, nothing to migrate back).
- **The "see all pending items" trigger** (`renderChecklistOverview()`, calling `pageTagHtml(onclick, label, true)`) is a `.pagetag.compact` tag rather than the old full-width `.addday` button. `compact`'s `position:absolute` against `#appCard` (the nearest positioned ancestor of `#checklistView`, same trick `.locbadge` uses against `.masthead`) — not a `.stackedpage`, since the overview itself is the base layer, not a stacked page — is specifically so it never takes up its own row: the overview's `<ul class="tasks">` starts right after `.quickadd` regardless of whether this tag is even present, unlike the old button which always pushed the list down by a full row whether or not there was anything pending. Don't reintroduce it as a block element; that's the exact thing this replaced.
- **The Daily tab** is a parallel view, not a category. `render()` branches between `#categoryView` and `#dailyView` based on `activeTab`. Both containers stay in the DOM; whichever one is inactive gets its `innerHTML` cleared on each render to avoid duplicate element IDs (task rows use `id="exp-<taskId>"`, which must stay unique). `renderDayDetail()`'s "pull in an existing task" list (`unplanned`) only offers a task with a due date if `isDueWithinDays(t.dueDate, 3)` — due today, already overdue (no lower bound: overdue is exactly the case worth catching up on), or due within the next 3 days; a dateless task stays unconditionally eligible, since there's no urgency window to apply to it. A task due further out than that isn't relevant to a specific day's plan yet, so it shouldn't clutter the picker. `renderDayDetail()`'s header also carries left/right `.navarrow` buttons (`goToAdjacentDay()`/`adjacentDayStr()` in `11-daily-core.js`) that step to the closest earlier/later day in `state.days` — chronological order, not the array's own newest-first insertion order — and render disabled (not hidden, not wrapping) at either end of your logged days. Pure navigation, same as `openDay()` itself: no `pushUndo`.
- **IDs**: use the `newId(prefix)` helper for anything created in a loop (e.g. duplicating tasks) to avoid `Date.now()` collisions. Simple one-off creations can still use `newId(...)` for consistency.

## Conventions

- No inline `style=` attributes for anything reused more than once — add a class instead.
- Keep the ledger/estate visual identity (Fraunces serif for display text, IBM Plex Sans/Mono for UI). Don't introduce a generic Tailwind-style look. The parchment-on-desk *colors* in `:root` are now just the default `theme` (see Theming below) — customizable per-user, not fixed — but they're still what every new account and the login screen sees, so treat them as "the" palette when nothing else is specified.
- Buttons that mutate state call `render()` (or a more targeted render function) **immediately** against the in-memory `state`, then `queueSave()` — never `await saveState()` before rendering. Saving is a real network round-trip to Supabase now, so awaiting it before `render()` makes every tap feel laggy; `queueSave()` chains onto `saveChain` so saves still land in the order they were made even though the UI doesn't wait for them. Follow this render-then-queueSave order for new mutations rather than reintroducing an `await saveState()` in front of a render.
- `sortTasks()` is the canonical sort (urgent first, then due date, done tasks last). Reuse it rather than re-sorting inline.
- Because `render()` rebuilds a view's whole `innerHTML`, any input inside that view is destroyed and recreated on every mutation — harmless for most fields, but fatal for an "add another one" input the user is meant to keep typing into after Enter (`.subadd`, `#checklistQuickInput`): the *new* input starts empty and unfocused, so without an explicit refocus, focus silently falls out of the field after the first entry. `addSubtask()` calls `focusVisibleSubadd()` and `addChecklistList()` refocuses `#checklistQuickInput` directly after their `render()` for exactly this reason — if you add another "type several in a row" input somewhere, it needs the same explicit refocus-after-render, `this.value=''` in the `onkeydown` handler alone won't do it (that clears the old, about-to-be-replaced element, not the new one).

## Testing locally

Run `python3 build.py` first if you've touched anything under `src/` — `priority-ledger.html` only reflects source changes after a rebuild. Then open `priority-ledger.html` directly in a browser, or:

```
python3 -m http.server 8000
```

`window.storage` won't exist outside claude.ai, so you'll land on the login screen. Either sign in with a real Supabase test account, or click "Continue without an account" to exercise the `localStorage` fallback — this is expected and is not something to "fix."

To skip the login screen entirely (e.g. Claude Code testing a UI change), append `?localdev=1` to the URL — it's equivalent to clicking "Continue without an account" but lands in the app on first paint, no click/JS-eval needed. Gated by `isLocalDevHost()` (localhost/127.0.0.1/file:// only) so it can never do anything on the real hosted site even if someone appends it there by mistake — it's a dev convenience, not a feature.

## After making changes

Run `python3 build.py` before committing anything that touches `src/` — do this automatically, don't wait to be asked. Commit both the `src/` changes and the regenerated `priority-ledger.html` together so the deployed file never drifts from source.

This repo's `main` branch is served directly by GitHub Pages. Pushing `priority-ledger.html` to `main` updates the live app at `https://chuckchuk.github.io/Priority-Ledger/priority-ledger.html` — always confirm with the project owner before pushing, since it's a real GitHub remote and the live site both users rely on.
